# PoC-бенчмарк пропускной способности (тикет #10, гейт Waltrail 07)

Гейт перед точкой невозврата фазы удаления (issue #3): замер трёх ступеней
конвейера CDC — **walsender** (МиБ/с WAL) → **intake** (декодирование и сборка
строк журнала в воркере) → **вставка в `changes`** — на потоке 200+ тыс.
событий/сек узкими и «аудитными» (~1 КБ) строками, вердикт go/no-go против
цели ≥167 тыс. событий/сек (10 млн событий/мин).

**Вердикт: NO-GO** — узкое место, ступень вставки в `changes`, 5–11 раз ниже
цели на железе стенда. План коррекции зафиксирован (см. [план коррекции](#план-коррекции))
и в [ADR-0003](../adr/0003-гейт-производительности-no-go-вставка-в-changes.md).
Примечание: целевой док `docs/цель-waltrail-архитектура.md` из issue #3 в
репозиторий не входил, поэтому решение зафиксировано в ADR — месте для
архитектурных решений по конвенции `docs/agents/domain.md`.

## Окружение

| Параметр | Значение |
| --- | --- |
| Железо | Apple M1 (8 ядер), 8 ГБ ОЗУ, APFS |
| Виртуализация | Docker Desktop (db-src и db1 на одном диске) |
| СУБД | PostgreSQL 17.4 (источник `db-src` с `wal_level=logical`, журнал `db1`), настройки по умолчанию (`shared_buffers=128МБ` и т. д.) |
| Воркер | `worker-cdc` (release), `CDC_BATCH_SIZE=500` по умолчанию, один слот `waltrail`, один поток репликации |
| Схема журнала | `changes`: 3 GIN (`jsonb_path_ops` по `before`/`after`/`context`) + 6 btree + 2 уникальных констрейнта, PK — случайный `uuid_generate_v4()` |
| Генератор | `scripts/loadgen/generate.py` (psycopg 3, серверная генерация через `generate_series`) |

## Методика

- **Поток** создаётся генератором: параллельные сессии, каждая транзакция —
  один `INSERT … SELECT generate_series(...)` на 10 тыс. строк
  (`payload` случайный md5-подобный текст заданного размера) с опциональным
  `pg_logical_emit_message` (префикс `_audit`, ADR-0002). Скорость генерации
  ограничена только диском источника.
- **Три ступени** измеряются инструментацией воркера (`worker_cdc::metrics`,
  сводка в лог каждые 10 с): байты потока репликации (walsender), счётчик
  собранных строк журнала и чистое время ступени intake, счётчик вставленных
  строк, длительности транзакций вставки (кольцо на 4096 батчей → p50/p99).
  «Занятость» ступени = её чистое время / время стены: конвейер
  последовательный, поэтому занятость прямо указывает узкое место.
- **Монитор стенда** (`scripts/loadgen/monitor.py`) сэмплирует скорость WAL
  источника, лаг слота (`confirmed_flush_lsn`) и объём `changes`.
- Перцентили считаются по длительностям транзакций вставки (одна транзакция
  источника = один батч вставки); при малом числе батчей в окне p99 близок
  к максимуму.

## Сценарий 1 — узкие строки (~100 Б payload)

Генерация 60 с: 3 сессии × 10 тыс. строк/транзакцию; следом за нагрузкой — слив бэклога из слота.

| Ступень | Наблюдение |
| --- | --- |
| Генерация потока | **17 730 000 строк за 60,7 с**: средняя **291 960 строк/с**, пик **497 826 строк/с** — цель «200+ тыс./сек» на генерации достигнута |
| walsender | 2–4,4 МиБ/с отданного потока — ступень сцежена вставкой (обратное давление сокета); источник при этом генерировал ~35 МиБ/с WAL |
| intake | 13–21 тыс. соб/с при **занятости 3–5%**; в пиках слива 34 тыс. соб/с при занятости 7% — экстраполированная ёмкость ≥400–500 тыс. соб/с |
| Вставка | **15–20 тыс. строк/с** под нагрузкой (занятость 88–98%), до ~35 тыс. строк/с в эксклюзивном дренааже |
| p50 / p99 батча (10 тыс. строк) | 378–436 мс / 1,1–1,8 с |

## Сценарий 2 — «аудитные» строки (~1 КБ) + MESSAGE

Генерация 45 с: 6 сессий × 10 тыс. строк/транзакцию, `pg_logical_emit_message`
каждую 4-ю транзакцию (90 MESSAGE).

| Ступень | Наблюдение |
| --- | --- |
| Генерация потока | **3 680 000 строк за 46,5 с**: средняя **79 080 строк/с**, пик **139 719 строк/с** — потолок генерации на этом диске (WAL источника 78–82 МиБ/с) |
| walsender | 12–17,6 МиБ/с отданного потока |
| intake | 12–17 тыс. соб/с при **занятости 3–4%** — не узкое место |
| Вставка | **12–17 тыс. строк/с** (занятость 90–98%) |
| p50 / p99 батча (10 тыс. строк) | 489–603 мс / 1,1–2,4 с |
| Слот | лаг `confirmed_flush_lsn` рос до **3,4 ГиБ**; после остановки генерации слит полностью: **4 284 703 строки** доставлены в `changes`, буферы → 0, потерь нет |

> Замечание к условию гейта: на «аудитных» строках поток 200+ тыс. событий/сек
> генератором на этом стенде не достигнут — потолок диска источника
> (~140 тыс. строк/с при payload ~1 КБ, WAL 78–82 МиБ/с). Условие спеки по
> потоку подтверждено на узких строках (291 960 строк/с в среднем); вставка
> сцеживала и меньший поток (лаг 3,4 ГиБ), поэтому вывод об узком месте от
> неполного покрытия условия не зависит.

## Пробы изоляции факторов (узкие строки)

| Проба | Эффект |
| --- | --- |
| Сняты 3 GIN-индекса | p50 вставки 430 → 290–300 мс (**−30%**), устойчивая скорость без значимого роста |
| `CDC_BATCH_SIZE` 500 → 2000 | p50 269–290 мс — в пределах шума |
| Нагрузка vs слив | под одновременной генерацией вставка 15–20 тыс./с, в чистом сливе до 35 тыс./с — дисковая конкуренция источника и журнала в одной VM отнимает у вставки ~40% |

## Сравнение с целью и узкое место

Цель: **≥167 тыс. событий/сек** сквозной пропускной способности.

| Ступень | Оценка ёмкости | Против цели | Вывод |
| --- | --- | --- | --- |
| walsender | источник декодирует и отдаёт поток, соответствующий генерации 200–400 тыс. строк/с (78–82 МиБ/с WAL) без деградации | запас | **PASS** |
| intake | ≥400–500 тыс. соб/с (занятость ≤7% на наблюдавшихся 35 тыс./с) | запас ≥2,4× | **PASS** |
| Вставка в `changes` | 15–35 тыс. строк/с (узкие), 12–17 тыс./с (~1 КБ) | **разрыв 5–11×** | **FAIL — узкое место** |

Конвейер последовательный: сквозная скорость равна скорости вставки,
walsender и intake простаивают (занятость ≤7%), буферы транзакций не растут
(обратное давление через слот работает, потерь и дублей нет).

Оговорка о железе: стенд — ноутбук M1 в Docker с диском по умолчанию;
серверное железо с NVMe и большим `shared_buffers` даст оценочно 2–4×, что
не закрывает разрыв 5–11×. Данные по ступеням (intake и транспорт с запасом,
вставка — провал) переносимы: узкое место локализовано в схеме записи
журнала (9 индексов, случайный UUID v4 PK, последовательная вставка чанков,
fsync на каждую транзакцию источника), а не в архитектуре «слот → воркер →
`changes`».

## План коррекции

Приоритизирован по отношению «эффект/цена»; пункты 1–5 — до заявки контракта
10 млн событий/мин, 6–7 — по ADR, 8 — «последняя миля».

1. **Разгрузить индексы `changes`.** Журнал write-heavy: вторичные индексы
   (6 btree: `table`, `operation`, `committed_at`, `primary_key`,
   `request_id`, `trace_id`) и GIN — кандидаты на перенос из горячего пути
   (отложенное построение, партиции). GIN дают ~30% цены вставки (проба).
   Ожидаемо: 1,3–1,5×.
2. **Партиционирование `changes` по времени** (`committed_at`): локальность
   индексов, дешёвый retention через DROP партиции, устойчивая скорость на
   растущем объёме (наблюдалась деградация p50 с ростом таблицы).
3. **Монотонный PK**: `uuid v4` → `uuidv7` (на PG 17 — на стороне воркера)
   — устраняет случайный thrash по PK и уникальному индексу. Ожидаемо:
   1,2–1,5×.
4. **Параллельная вставка чанков**: сейчас чанки одной транзакции вставляются
   последовательно; пул к БД аудита (5 соединений) позволяет параллелить.
   Ожидаемо: 2–3× на дисках с очередями.
5. **COPY вместо `INSERT … VALUES`** для чанков (`sqlx` `copy_in`): дешевле
   разбор запросов и передача по сети. Ожидаемо: 1,5–2×.
6. **`synchronous_commit=off` для сессии вставки журнала**: цена — окно потери
   хвоста при крэше БД аудита; компенсируется replay-дедупликацией
   (at-least-once + ключ `(commit_lsn, event_index)`) и чекпоинтом.
   Требует отдельного ADR.
7. **Деление слотов / шардинг** (вариант из тикета): масштабирует walsender и
   intake, вставку — только вместе с п. 2 и 4; цена — повторное декодирование
   на каждый слот и рост «в буферах». Инструмент горизонтального масштаба
   после п. 1–6.
8. **Резать payload** (вариант из тикета): хранить в `before` только
   изменённые колонки, ограничить размер payload — ломает контракт полных
   образов (ADR-0002), применять после п. 1–7 при недоборе.

## Воспроизведение

```bash
docker compose up -d
cargo build --release -p worker-cdc

# воркер (сводки метрик — каждые 10 с в лог; info легаси-строк приглушён)
SOURCE_DATABASE_URL=postgresql://postgres:postgres@localhost:54398/postgres \
DATABASE_URL=postgresql://postgres:postgres@localhost:54399/postgres \
RUST_LOG="warn,worker_cdc::metrics=info" ./target/release/worker-cdc

# генерация: узкие строки, 3 сессии × 10 тыс. строк/транзакцию, 60 с
.venv/bin/python scripts/loadgen/generate.py \
  --duration 60 --sessions 3 --rows-per-tx 10000 --payload-bytes 100

# «аудитные» строки + MESSAGE каждые 4 транзакции
.venv/bin/python scripts/loadgen/generate.py \
  --duration 45 --sessions 6 --rows-per-tx 10000 --payload-bytes 1024 \
  --message-every 4

# монитор стенда: WAL источника, лаг слота, объём журнала (CSV на stdout)
.venv/bin/python scripts/loadgen/monitor.py --duration 120 > monitor.csv
```

Числа этого отчёта сняты 2026-10-21 на описанном стенде; абсолютные значения
воспроизводятся с разбросом ±20% (общий диск двух СУБД), соотношение ступеней
и вывод устойчивы.
