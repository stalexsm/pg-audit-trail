# ADR-0002: Одна сущность журнала `changes`, непрозрачный trace_id, один канал контекста

Журнал хранит всё в одной таблице `changes`: изменения строк (I/U/D/T) и события приложения — строками с операцией `MESSAGE` (payload в `context`). Отдельной таблицы событий приложения с типизированными колонками (status_code, response_body) нет — это специфичное для исходного заказчика требование, чужое универсальному продукту. Идентификатор сквозной операции — колонка `trace_id`: непрозрачная строка клиента (ключ `trace_id` верхнего уровня в payload MESSAGE копируется воркером в колонку и проставляется всем строкам транзакции; сам payload сохраняется в `context` дословно, без вырезания ключа); Waltrail её значение не интерпретирует. Контекст передаётся единственным каналом — `pg_logical_emit_message` в транзакции клиента; HTTP-приёмник не строится.

## Considered Options

- **Две таблицы (changes + audits) со связкой request_id = audits.id::text** — отклонено: требовало клиентского генератора uuid, второго транспорта (HTTP) и не универсально.
- **MESSAGE только обогащает строки, своих записей не создаёт** — отклонено: события без изменений строк не попали бы в журнал.
- **trace_id только внутри context JSONB, без колонки** — отклонено: главный сценарий API («вся операция пользователя») остался бы на медленном GIN-фильтре без индекса равенства.
- **Вырезание `trace_id` из payload (в `context` — остаток)** — отклонено: клиент ожидает видеть отправленный payload в журнале неизменным; колонка — производная копия верхнего ключа, расхождений между ней и `context` нет по построению.
- **Слияние контекстов нескольких MESSAGE одной транзакции** — отклонено: строки получают контекст последнего MESSAGE (все MESSAGE-строки сохраняются; коллизия — warn в лог).

## Consequences

- status_code/response_body не типизированы: фильтрация по ним — GIN по `context`, контракт полей payload — забота клиента.
- Контракт payload MESSAGE (`trace_id` верхнего уровня) — публичный API для будущих SDK; менять больно.
- Payload обязателен JSON (JSONB в журнале): не-UTF8 или не-JSON payload события приложения в журнал не попадает (warn в лог воркера), на поток репликации это не влияет.
- Идентификатор длиннее колонки `trace_id` VARCHAR(255) обрезается воркером (без обрезки падала бы вся транзакция вставки); payload в `context` сохраняется целиком.
- Клиент обязан уметь вызывать `pg_logical_emit_message` в транзакции (до SDK — SQL-сниппеты в документации).
