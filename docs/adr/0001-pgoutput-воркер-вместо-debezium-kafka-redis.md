# ADR-0001: Собственный pgoutput-воркер вместо Debezium + Kafka + Redis

CDC-инжест журнала реализуется одним Rust-процессом `worker-cdc`, который читает логическую репликацию PostgreSQL напрямую (pgoutput, `START_REPLICATION … messages=true`), а не через Debezium Connect + Kafka. Решение закрыло известные дефекты цепочки (retention Kafka, at-most-once чекпоинты, потеря контекста на границах батчей, regex-парсинг SQL) и убрало JVM-обвязку (~1,5 ГБ RSS, p99 ~900 мс → один процесс ~60 МБ, p99 ~70 мс) — единственная топология, заимевшая запас к цели ≥167 тыс. событий/сек.

## Considered Options

- **wal2json + Rust** — запасной план: C-плагин в БД клиента, ~7,6 тыс. событий/сек end-to-end, деградация на больших транзакциях.
- **Outbox-триггеры, LISTEN/NOTIFY** — не подходят: нет before/after и txid/commit_ts; потери при офлайне.
- **Готовые движки (Sequin, supabase/etl, pgstream)** — не встраиваются: Elixir или нестабильный API, поддержка MESSAGE-событий не подтверждена; используются как образцы кода.
- **Очередь на Postgres (SKIP LOCKED)** — ~22–48 тыс. сообщ/сек на узел: только как служебный механизм, не транспорт.

## Consequences

- Слот репликации сдерживает WAL источника: обязателен мониторинг `confirmed_flush_lsn` и `max_slot_wal_keep_size` (иначе молчаливая инвалидация слота = потеря событий).
- Логический слот не переезжает на standby автоматически: PG 17+ failover slots, для старых — runbook пересоздания.
- Kafka, Redis, Debezium и крейты `worker-app`/`worker-debezium` удалены; реконфигурация транспорта в будущем = переписывание инжеста.
