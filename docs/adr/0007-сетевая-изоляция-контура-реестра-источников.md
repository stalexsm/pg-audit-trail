# ADR-0007: Сетевая изоляция контура реестра источников — мутации только из изолированной сети

Аутентификации в Waltrail нет, и [ADR-0005](0005-мультиисточность-через-реестр-источников.md) принял этот риск «наравне с остальным API» — но та формулировка построена вокруг чтения журнала и не покрывает жизненный цикл источников: мутации реестра (`POST`/`PATCH`/`DELETE /api/sources`) — привилегированные операции, меняющие репликационную конфигурацию клиентских баз (публикации и слоты). Граница доверия фиксируется явно — сетью: мутации реестра допустимы только из изолированного контура, API не публикуется наружу; доступ к API из недоверенной сети (интернет, общая сеть) — нарушение эксплуатационного требования, а не поддерживаемый сценарий. По коду ничего не меняется: решение — изоляция и документирование (требование в README, разделы запуска и безопасности), аутентификация не вводится. ADR-0005 задним числом не переписывается: его оговорка отныне читается как «чтение — наравне, мутации — только из изолированного контура».

## Considered Options

- **Аутентификация мутаций (токен на POST/PATCH/DELETE)** — отклонено: в системе появляется первый секрет — хранение, раздача, ротация; утечка токена переносит вектор, а не закрывает его. Решение об аутентификации принимается отдельно, при появлении внешнего контура.
- **Разделение API на два сервиса: публичное чтение журнала и внутренний API реестра** — отклонено: удвоение деплоя и кодовых путей ради границы, которую без единой строчки кода даёт сеть; внутри изолированного контура это лишняя движущаяся часть.
- **Сетевая изоляция + документирование** — принято: API публикуется только в изолированном контуре; операционная обязанность — не выставлять порт API в недоверенные сети (зафиксирована в README).

## Модель угроз

Анонимная мутация из недоверенной сети даёт атакующему:

- **Blind-SSRF с ошибкой-оракулом**: `POST /api/sources` принимает произвольный url — воркер открывает соединение на заданный `host:port` внутреннего периметра; статус и текст ошибки читаются из реестра (`GET /api/sources`), то есть по ответу API различают «порт открыт / закрыт» и видят текст ошибки подключения (вплоть до диагностики протокола внутренней базы).
- **Мутацию репликационной конфигурации внутренних баз**: на зарегистрированном «источнике» воркер создаёт публикацию `audit_<имя>` и слот `waltrail_<имя>` — публикация меняет конфигурацию чужой базы, слот удерживает её WAL.
- **Остановку сбора одной командой**: `DELETE /api/sources/<имя>` помечает боевой источник к удалению — воркер останавливает сбор и дропает у клиента слот и публикацию; перерегистрация создаёт новый слот с текущей позиции WAL клиента — непрочитанный хвост в журнал не попадает.

Анонимное чтение журнала и реестра вне границы этого ADR: принятый риск ADR-0005, смягчённый маскированием url в ответах (тикет #38); модель угроз здесь ограничена мутациями.

## Consequences

- **Требование к деплою**: порт API публикуется только в изолированном контуре (приватная подсеть, внутренняя docker-сеть; операторы — через bastion/VPN); в dev-стенде `8000` на хосте — исключение локальной разработки, а не образец для прода. Контроль периметра (firewall/ACL) — обязанность оператора.
- **Сеть — единственная защита**: компенсирующих механизмов в коде нет; нарушение изоляции означает полный анонимный контроль над жизненным циклом источников плюс зондирование внутреннего периметра (модель угроз выше).
- **Условия пересмотра**: решение пересматривается при любом из событий — API становится доступен из недоверенной сети (публичный сервис, мультиарендность, self-service внешних клиентов), появляется требование аудита или разграничения мутаций, доверие операторов разделяется. Тогда принимается отдельное решение (аутентификация мутаций либо разделение API на публичное чтение и внутренний реестр), настоящий ADR заменяется.
