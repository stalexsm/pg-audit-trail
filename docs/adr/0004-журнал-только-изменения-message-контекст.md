# ADR-0004: Журнал — только изменения строк; MESSAGE — канал контекста, а не сущность журнала

*Supersedes: [ADR-0002](0002-одна-сущность-changes-trace_id-один-канал.md) в части MESSAGE-строк (сам ADR-0002 задним числом не переписывается).*

Единственное содержимое журнала `changes` — изменения строк источника (CREATE/UPDATE/DELETE/TRUNCATE). MESSAGE (`pg_logical_emit_message` в транзакции клиента) — только канал контекста: payload MESSAGE обогащает `context` и колонку `trace_id` строк **той же транзакции**, но сам строкой журнала не становится. События приложения без изменений строк в журнал не попадают: если приложению нужен собственный журнал событий, оно пишет его само. Контракт обогащения — «последний побеждает»: при нескольких MESSAGE в одной транзакции все её строки (включая строки до MESSAGE) получают payload последнего, коллизия — warn в лог воркера; транзакция — атомарная операция клиента, при необходимости разделить запросы клиент разносит их по разным транзакциям. Нумерация `event_index` по-прежнему учитывает MESSAGE: индекс обязан быть детерминированной функцией содержимого транзакции, иначе replay-дедупликация по `(commit_lsn, event_index)` сломается. Решение владельца (обсуждение при закрытии #11, тикет #20).

## Considered Options

- **MESSAGE-строки в журнале (ADR-0002)** — отклонено: события дублировали контекст уже записанных строк той же транзакции, а «журнал событий» без связи с данными — забота приложения, не аудита изменений.
- **Обогащение с привязкой к таблице (как в удалённом легаси worker-debezium)** — отклонено: там контекст связывался со строками по `(transaction_id, таблица)`, где таблица вытаскивалась regex'ом из SQL-текста в payload. Payload MESSAGE — произвольный JSON без гарантий структуры; хрупкий разбор SQL и зависимость от regex-паттернов не восстанавливаются, областью обогащения остаётся транзакция.
- **Позиционное обогащение (контекст ближайшего MESSAGE перед строкой)** — отклонено: точнее связывает «запрос → изменение», но усложняет контракт ради сценария «несколько запросов в одной транзакции», который клиент решает разделением транзакций.
- **MESSAGE только обогащает строки, своих записей не создаёт** — принято (снимая оговорку ADR-0002 о «событиях без изменений строк»): контекст и так сохраняется в `context` всех строк транзакции, отдельная запись его не добавляет.

## Consequences

- Транзакция «INSERT + MESSAGE» даёт в журнале ровно одну строку (INSERT); транзакция только с MESSAGE не создаёт строк и не мешает ack слота/чекпоинту (чекпоинт продвигается пустой вставкой).
- Словарь операций журнала — CREATE, UPDATE, DELETE, TRUNCATE; операция MESSAGE из API-фильтров и документации уходит.
- Контракт payload MESSAGE (`trace_id` верхнего уровня, произвольный остальной JSON) не меняется — он по-прежнему публичный API для будущих SDK.
- Префикс MESSAGE, интерпретируемого как канал контекста, настраивается (`CDC_MESSAGE_PREFIX`, по умолчанию `_audit` — историческое значение легаси-пайплайна); MESSAGE с другими префиксами строкам контекст не меняет.
- «Вся операция по trace_id» в API возвращает только изменения строк; дедупликация и чекпоинты не меняются.
- Клиент, которому нужен журнал событий приложения, ведёт его сам: Waltrail не обещает строк событий в журнале.
